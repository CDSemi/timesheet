## Required changes (binding)

1. **Correction revisions.** A correction of a finalized period requires a reason and
   creates a new immutable revision (supersedes link). It posts only differences:
   - a day that already has a posted original credit or debit: `postCorrection` with a
     revision-specific key `rev:{revisionId}:day:{date}:correction`, handling the
     `unchanged` and `pending` outcomes (pending per F-2: a recorded pending line,
     re-evaluated only by a later finalized revision);
   - a day without a posted original (for example a day that had no records when the
     period was submitted automatically, F-1): post a first credit or debit with the
     day's revision-independent original key, not a correction (WP3-REQ O7);
   - every outcome is recorded in `revision_ledger_lines`.
2. **R1.** Add `sourceRef` to the `postCorrection` duplicate comparison (red-first): a
   retry with the same key but a different source is refused, not silently accepted.
3. **Late review.** The owner's late review of an automatic revision creates a signed
   revision with zero ledger delta when the content is unchanged (LG-09) and an explicit
   `send_email` choice (no job when false).
4. **Resend.** `POST /api/revisions/:id/resend` creates a new delivery attempt on the
   same revision with no ledger movement; refused while an attempt is `sending` or
   `uncertain` without an explicit decision; a changed envelope (recipients, template)
   requires a new revision instead.
5. Original revisions, PDFs and sign-offs stay untouched. Every route is owner-only
   (another user 404, anonymous 401). No network call inside a transaction.

#### Behaviour

- `POST /api/timesheets/:payrollDate/revisions` (correction): body = the sign-off fields plus `reason` (required,
  blank 422 `reason_required`, max 2000) and `send_email` (required boolean, no default). One IMMEDIATE transaction:
  409 `not_finalized` for an unfinalized period; replay of an identical retry (200 `replayed`); 409 `stale_version` /
  `stale_review` (hash binds the review); the sign-off checks (name, current signature, acknowledgement, choose-mode
  choices for every choose-mode deficit day); a `correction` revision (revision_no + 1, supersedes the current one,
  `correction_reason`) with a real sign-off; differences posted; `finalized_revision_no` moved with a guarded UPDATE; jobs;
  audit (reason, ids, counts; never the signer name).
- Differences (`postDifferences`, ledger only through `ledger.ts`): debit-side days first, then credit-side days (the
  sign-off order). Per day, a posted original credit or debit (original key `finalization:day:{date}:credit|deficit_debit`)
  is corrected with `postCorrection`, key `rev:{revisionId}:day:{date}:correction` (`:2` when a second correction posts on the
  same day), `sourceRef` = revision id, the reason, `expectedPreviousMinutes` = the value computed from the ledger. A day
  without a posted original gets a first credit (`postCredit`) or first debit (`postDeficitDebit`) with the day's
  revision-independent original key (WP3-REQ O7); this is also how a later revision re-evaluates a pending debit (F-2).
  Days with unresolved records (incomplete, incomplete breaks, calculation error) are left as the ledger holds them.
- Lines (`revision_ledger_lines`): `unchanged` (kind `correction`, 0 minutes, links the original entry; dropped only when a
  real line takes its day/kind slot), `posted` corrections (kind `correction`, signed difference), a debit increase is a new
  debit of the increase (R-05) and so a `deficit_debit` line (negative minutes) that is `posted` or
  `pending_insufficient_balance` (nothing appended, shown by `GET /api/revisions/pending-lines`; only a later finalized
  revision re-evaluates it), first credit `credit`, first debit `deficit_debit`, `waived`.
- R1: the `postCorrection` duplicate branch compares `sourceRef` too (same key, other source: 409 `source_key_conflict`).
- `POST /api/timesheets/:payrollDate/late-review`: only for the current revision when it is an automatic one awaiting review
  (409 `no_pending_review` otherwise, 409 `not_finalized` before any revision). Creates a `late_review` revision (signed,
  supersedes the automatic one, no reason) with a real `signed_at`. The ledger-relevant content (credits and deficit
  minutes per day) must equal the automatic revision's, else 409 `content_changed` (use a correction with a reason); so the
  difference is zero (LG-09): all lines `unchanged`, no ledger row, no ledger audit. Choose-mode deficits that stayed
  pending at the automatic submission need a choice and post as first debits.
- `send_email` is stored as `send_requested`. Interpretation to confirm: `false` enqueues only the `render_pdf` job (every
  signed revision keeps a PDF) and no `send_email` job; `true` enqueues both with the T05 business keys.
- `POST /api/revisions/:id/resend` (body: optional `to`, `cc`, `template_version` echoes): owner-only (another user or an
  unknown id 404). Refused with 409 for a superseded revision (`revision_superseded`), a changed envelope (`envelope_changed`,
  `new_revision_required`), an attempt `preparing`/`sending` or a queued/leased send job (`delivery_in_progress`), an
  `uncertain` attempt without a decision (`delivery_uncertain`; a recorded `resend` decision lifts it) and no ready PDF
  (`pdf_not_ready`). Otherwise it inserts a new `send_email` job (key `revision:{id}:send_email:resend:{n}`) and a
  `preparing` delivery attempt (frozen envelope from the revision's own payload: recipients, subject, template version,
  body digest, PDF hash; stable `<uuid@timesheet.invalid>` Message-ID; attachment = the ready PDF) and one audit event
  without recipients. No revision, sign-off, line, ledger or timesheet row changes.
- Originals stay untouched (test compares the stored revision, sign-off, lines, jobs and ledger entries before and after).

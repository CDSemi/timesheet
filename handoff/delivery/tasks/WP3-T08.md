#### Job store (`jobStore.ts`)

- `enqueueJob`: one `INSERT ... ON CONFLICT (business_key) DO NOTHING`, then the stored row; returns
  `{job, created}`. A duplicate key (including the T05 sign-off keys) returns the existing job unchanged. Safe inside a
  caller's transaction.
- `claimNextJob({owner, kinds, leaseSeconds})` inside BEGIN IMMEDIATE: first an expired lease that already used the last
  attempt goes to `intervention` (`lease_expired`); then one
  `UPDATE jobs SET state='leased', lease_owner, lease_expires_at = now + lease, attempts = attempts + 1 ... WHERE id =
  (SELECT ... kind IN (handler kinds) AND ((queued AND next_run_at <= now) OR (leased AND lease_expires_at <= now))
  ORDER BY next_run_at, created_at, id LIMIT 1) RETURNING *`. A runner never claims a kind it has no handler for (the
  `send_email` jobs stay queued until T09). Default lease 120 s.
- `renewLease`, `completeJob` and `failJob` all require `state = 'leased' AND lease_owner = <owner>`; a runner that lost
  its lease changes nothing (`false` / `{state: 'lost'}`).
- Retry policy: `RETRY_DELAYS_MINUTES = [1, 5, 15, 60]`, `MAX_ATTEMPTS = 5`: failed attempt n (n = 1..4) is queued at
  now + delay[n-1]; the fifth failure, a permanent `JobError`, or an expired lease on the fifth attempt gives
  `intervention`.
- Redaction: `last_error` holds only a `JobError` code (`^[a-z][a-z0-9_]{0,59}$`, checked in the constructor);
  anything else is stored as `internal_error`. Messages are never stored.
- `recordHeartbeat` writes `operations_state.runner_heartbeat_at` and an opaque `runner_instance`
  (`runner-<12 hex>`, no host or user name).

#### Runner (`runner.ts`), server entry and CLI

- `runJobsOnce({db, clock, handlers, owner?, leaseSeconds?, maxJobs?})`: heartbeat, then claim, run, complete or fail
  until no job is due (cap 100); handlers run outside any transaction with a renewal timer at a third of the lease.
  Returns counts `{claimed, succeeded, retried, intervention, lost}`. `createJobHandlers({db, clock, files})` is the
  production registry (`render_pdf` now).
- `startJobRunner`: a pass at start and every 15 s (timers unref'd); a failed pass logs only a redacted code; `stop()`
  waits for the pass in progress. `index.ts` starts it unless `JOB_RUNNER=off` and stops it on SIGINT/SIGTERM before
  closing the database. `createApp` (tests) never starts a runner.
- Carry item: `index.ts` calls `loadDeliveryConfig(process.env, config)` and passes `{dataDir}` to `createApp`; the
  runner's file store uses the same directory.
- `cli.ts run-jobs --once --now <YYYY-MM-DDTHH:MM:SSZ>`: refused with exit 1 when `NODE_ENV=production`, checked before
  any configuration is read or any file is opened; other argument lists exit 2 with the usage line; otherwise migrate,
  run one pass on a fixed clock and print the counts JSON (no ids, names or paths).

#### PDF job (`pdfJob.ts`)

- Loads the revision by `(id, user_id)` from the job (the payload `revision_id` must match); a `ready` revision file
  ends the job without work (idempotent).
- Marks `revision_files` `pending` (insert, or `failed` -> `pending`), re-checks the payload SHA-256 and renders with the
  T07 renderer from the stored snapshot only: `submissionId` = snapshot submission id, `revisionNo` from the row; a
  signed revision uses its sign-off `signed_at` and the image of `snapshot.signature`, which must be the sign-off's
  attachment; the bytes are read by attachment id and checked against the reviewed hash and the attachment row hash.
  An automatic revision (no sign-off) passes `signedAt` null and the authorized auto-image, if any, verified against its
  row hash.
- Writes `tmp/<random>.tmp` (0600, fsync) in the private store, then renames it to a deterministic opaque key
  `base64url(sha256("timesheet-revision-pdf\n" + revision id + "\n" + pdf sha256))`; an identical finished file at that
  key is kept. One transaction inserts the immutable `pdf` attachment (sha256, size) and sets the revision file `ready`.
  A killed runner that resumes renders the same bytes to the same key, so there is never a second file.
- Failures: `render_failed`, `pdf_write_failed` and `signature_unreadable` retry the same snapshot;
  `signature_hash_mismatch`, `signature_reference_mismatch`, `signature_missing`, `snapshot_hash_mismatch`,
  `revision_not_found` and `invalid_job_payload` are permanent (intervention). The revision file becomes `failed` with
  the same code. Nothing is posted to the ledger, no delivery attempt or audit row is written and no mail is sent.

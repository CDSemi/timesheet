## Required changes (binding)

1. **Private file store** (`src/server/files/fileStore.ts`): write to a temp file, then
   atomic rename; record SHA-256; opaque keys (no user-supplied names in paths); an orphan
   temp sweep that never removes a file referenced by `attachments`. Nothing is ever
   served from the static root.
2. **Image check** (`src/server/files/imageCheck.ts`): accept only PNG and JPEG; the magic
   bytes and the declared content type must agree; bounded pixel dimensions; truncated or
   polyglot input is refused.
3. **Signature service and routes**:
   - `POST /api/signatures` accepts a raw `image/png` or `image/jpeg` body with a
     route-scoped size limit (default 256 KiB). The global 64 KiB JSON-only rule stays in
     force for every other `/api/*` route; prove it with a test. Origin/CSRF checks are
     unchanged for this route.
   - An owner-only `GET` returns the image with `Cache-Control: no-store` and an
     attachment disposition. Another user's ID gives 404; anonymous gives 401.
   - Replacing the profile signature creates a new immutable attachment; earlier
     attachment bytes and hash stay unchanged (later revisions reference them).
   - Audit the upload without storing image bytes or personal data in the audit payload.

#### Behaviour

- File store: `put` writes `tmp/<random>.tmp` (mode 0600, fsync), then an atomic rename to
  `files/<24 random bytes, base64url>`; records SHA-256 and size; keys are opaque and every path is built only
  from a key matching the `attachments.storage_key` alphabet. `sweep({isReferenced, minAgeMs})` removes stale
  temp files and unreferenced objects only after a grace period and never a referenced file.
- Image check: PNG and JPEG only; the declared type and magic bytes must agree (415 otherwise, also for an
  unsupported declared type); max 4096 px per side and 8,000,000 pixels; PNG chunk CRCs, header validity and the
  inflated pixel length must match the header; JPEG must reach EOI; bytes after PNG IEND or JPEG EOI
  (polyglot) and truncated data give 422 `invalid_image`.
- Routes and limits:
  - `POST /api/signatures`: raw `image/png` or `image/jpeg`, route limit 256 KiB (`signatureMaxBytes` option),
    413 above it. Order: origin check (403), authentication (401, no body read), content type (415), size (413),
    image check (415/422). Returns metadata only (id, mime, size, pixels, sha256, created_at) with 201.
  - `GET /api/signatures/current` returns the caller's latest signature metadata (404 if none).
  - `GET /api/signatures/:id` returns the image: owner-scoped (another user, including an administrator, a
    non-UUID id, a storage key and unknown ids all give the same 404; anonymous 401), `Cache-Control: no-store`,
    `Content-Disposition: attachment; filename="signature.png|jpg"`, `nosniff`; bytes whose hash no longer
    matches the row are never returned (500).
  - Global rule kept: `/api/*` keeps 64 KiB and JSON-only everywhere else. The exception is an exact
    `POST /api/signatures` predicate (`unless()` in `security.ts`); the origin/CSRF middleware still runs for it.
- Replacement appends a new immutable attachment (earlier row, file bytes and hash unchanged; test also checks
  the immutability triggers). Per-user cap of 50 stored signatures (immutable rows cannot be deleted).
- Audit `signature.upload`: attachment id, mime, size, pixels, sha256, replaced attachment id; no bytes, key,
  name or email (test asserts the exact key set).
- `createApp(deps, options?)` takes `{dataDir, signatureMaxBytes}`. Default data dir is `private-data` beside
  the database (the same default as `loadDeliveryConfig`). `createApp` throws if the data dir is inside the static
  root or if the database is `:memory:` without a `dataDir`.

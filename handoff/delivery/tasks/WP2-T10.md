  - a choice when a local time does not exist (the gap);

  for business rules beyond what the contract requires. Device-zone changes must not

#### Contract mapping (the client sends exactly the server contract)

- Session body: `start` and `end` are `{local: "YYYY-MM-DDTHH:MM[:SS]", zone: <input zone>, fold?, offset?}`. Each of
  start and end has its own date field, so an overnight end date is explicit; `input_zone` is typed or picked
  explicitly (default: the reporting zone, never the device zone). No UTC instant is computed for the request.
- DST fold: the client submits first; the server answers 422 `ambiguous_local_time` with `details.offsets`
  (earlier first). The form then asks "Earlier time, UTC offset +11:00" or "Later time, UTC offset +10:00" and resends
  `fold: 0|1`. A saved or suggested time is pinned with `offset`, so a resave never asks again. A typed change clears
  the fold or offset.
- DST gap: 422 `nonexistent_local_time` is explained; the user edits the time or presses "Use 03:30 on 2026-03-08"
  (first valid time).
- Breaks: three outcomes through radios (not confirmed yet = `breaks_confirmed:false`; confirmed as listed; no
  breaks taken = `[]` confirmed) plus "Suggest breaks" and "Confirm suggested breaks". Clock out follows E-1:
  pending omits `breaks`; confirmed or none sends the complete list; `expected_version` is the running session's
  version. Confirming breaks that end after the Clock out is refused by the server and shown.
- Day fields: `PUT /api/days/:date` with `expected_version` (null without an entry), category, `leave_minutes`,
  `leave_kind`, WFH, notes. The E-2 notice is shown from `day.ot_leave.mismatch`; the e2e asserts that no `/api/ot`
  request is made.
- Reason: a textarea appears when `day.edit.reason_required`; saves are disabled without it and it travels as
  `reason`. Stale: any 409 `stale_version` shows "This day changed since it was loaded. Nothing was saved." with
  "Reload day" (Clock out has its own dialog message and "Reload").
- Upcoming: `completenessOf(day, todayLocal)` maps an expected day with no session after `today_local` (from
  `/api/periods/current`, re-read on each load) to `upcoming`; weekends and days with sessions are unchanged. The
  device clock is not used.

#### Contract gaps and observations (no server code was edited)

1. No server field or endpoint provides the expected finish or break suggestions. The editor calls the shared pure
   domain functions (`suggestBreaks`, `expectedFinishUtc`, and `resolveLocalDateTimeCompatible` for the gap
   shortcut) with the policy from `GET /api/policies`. These are display and prefill values only; the server still
   validates every body and computes all minutes. If the owner wants a strictly server-provided expected finish, a
   field on the day view is needed (WP3 or a later fix).
2. `ambiguous_local_time` details carry `local`, `zone` and `offsets` but not the field name, so the form matches the
   echoed local string against start, end and break fields.
3. A gap is only rejected by the server; "Use the first valid time" is a client suggestion pinned by an explicit
   offset and still validated by the server.
4. The day view carries no "today"; the client uses `today_local` from `/api/periods/current`.
5. `findRunningSession` only searched the displayed and the current payroll period; it now also searches the
   in-progress period (found by reading the code; the old behaviour was not reproduced in a browser).

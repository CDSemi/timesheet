## Binding decisions

- **E-4.** A holiday import preserves employees' explicit day labels and manually added
  calendar dates. A manual date goes away only when it is removed explicitly. Default
  labels follow the calendar at read time, so the import never writes employee rows.
- **E-10.** A payroll exception refreshes the stored `pay_periods` row in the same
  transaction when no finalized timesheet references the row. Otherwise it is refused.
- **E-12.** From 1 October, warn when next year's company calendar dates are missing. Use
  an injected or fixed clock in tests; never depend on the real current date.

#### Import rules

- CSV is `date,name[,kind]`, optional header, BOM, CRLF, quoted cells; at most 500 rows and 120-character names. Issues:
  `invalid_date, duplicate_date, empty_name, name_too_long, invalid_name, invalid_kind, out_of_year, formula_cell`
  (`= + - @` tab CR, in any cell), `wrong_column_count, unterminated_quote, too_many_rows`. A row with any issue never reaches the diff.
- The import is a merge into the latest version (highest effective date, then sequence). Dates the CSV does not list are kept,
  manual ones included. Only dates in `remove_dates` go away (E-4). Removal problems:
  `remove_not_found`, `remove_conflicts_with_csv`, `remove_before_effective_from`.
- CSV rows dated before `effective_from` are reported as `ignored_past` and not applied, so past classification cannot move.
- Preview reports the diff (added, renamed, kind_changed, removed, unchanged_count, kept, ignored_past), `affected_days`
  (per changed date: before/after default label and the counts of default-labelled entries and preserved explicit overrides in
  unfinalized timesheets of users on that calendar; counts only, no identity), `finalized_conflicts`, `earliest_effective_from`,
  `can_commit` and `preview_hash` (null unless it can commit).
- `preview_hash` is the SHA-256 of the calendar id, effective date, weekdays and the complete resulting date rules, so a changed
  CSV, date or concurrently changed calendar makes it stale, while a repeat of an applied import hashes the same.
- Commit refuses, in order: CSV or removal problems (422 `invalid_holiday_import`), `effective_from` before the prospective
  boundary (422 `retroactive_change`) or before the latest version (422 `effective_from_before_latest_version`), an added, removed
  or re-kinded date inside a period with a finalized timesheet (409 `finalized_period_affected`), a stale hash (409 `stale_preview`).
  Then it either returns the no-op or appends one immutable version with one `calendar_version.create` audit event
  (reason = note, `after.import` summary), all in one IMMEDIATE transaction. Employee rows are never written.

#### Payroll exceptions (E-10)

- Reason required (422 `reason_required`). In one transaction: validate, record the exception, refresh the stored
  `pay_periods` row (payroll date, due date and time, `due_at_utc`, `is_exception`; id, index, start and end stay) and write one
  `payroll_exception.create` audit event with the row before and after. If any user's finalized timesheet references the row:
  409 `period_finalized`, nothing changes. A duplicate nominal date is 409 `payroll_exception_exists`. Without a stored row only
  the exception is recorded, and the row is created with it later. A forced audit failure rolls back both writes (tested).

#### Calendar reassignment finding (report only; users.ts untouched)

`PATCH /api/admin/users/:id {calendar_id}` is defective for a user who already has data (probe:
`calendar-reassignment-probe*.txt`, same session cookie after the PATCH):

1. Draft days regroup. Calendar A gave period 2026-09-28 to 10-11 (payroll 10-16); B (anchor 10-05, zone Asia/Ho_Chi_Minh) gives
   10-01 to 10-14 (payroll 10-19). `today_local` moves 10-09 to 10-10. `GET /api/timesheets/2026-10-16` becomes 422
   `unknown_payroll_date`.
2. Days relabel and recalculate: the default-labelled 10-07 changes Worked to Holiday and credited minutes 0 to 60 (B's holiday).
   Explicit labels survive.
3. Existing timesheets are orphaned, not moved: the stored timesheet and its day entries stay bound to calendar A's
   `pay_periods` rows (A's reporting zone and stored due dates remain in the database), but reads join through B and show
   `id: null, version: 0`.
4. A finalized timesheet is hidden: the stored `finalized_revision_no = 1` is intact, yet the view reports `finalized: false`
   with no timesheet. Edits then follow the new calendar's relation, and a new timesheet row can be created for B's overlapping
   period.
5. Session `work_date` and `input_zone` values are unchanged, so the accounting dates themselves do not move; only grouping,
   labels and the effective reporting zone do (AGENTS rule 7, R-07).

Suggested fix for the coordinator to schedule (users.ts, outside T08): refuse a calendar change (409) while the user has any
timesheet, day entry or session, or require an explicit documented migration; the calendar may change only for an unused account.

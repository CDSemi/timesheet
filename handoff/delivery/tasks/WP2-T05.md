#### Behavior

- `ensureDayEntry` (session create, update, delete, Clock in and out) writes `category_source`
  'default'. A default row reads its label from the calendar at read time (`effectiveCategory`,
  `resolveDayCategory`). An explicit row keeps its label. The view adds `category_source`,
  `leave_minutes`, `leave_kind`, `wfh` and `ot_leave {kind_minutes, consumed_minutes,
  reversed_minutes, mismatch}`. `mismatch` is `kind_minutes !== consumed - reversed`. It is
  informational only; the warning UI is T10/T11.
- A day save, `PUT /days/:date` or batch, is always explicit. It validates leave against the
  effective B (`leave_exceeds_required`, `leave_kind_required`, `leave_kind_without_minutes`,
  `invalid_leave_kind`, `policy_missing`). There is no OT-funded category, and a kind or label
  change never touches the ledger (LG-10 extended, including a batch).
- `POST /api/days/batch` with `mode` preview|commit:
  - Omitted entry fields keep the existing values.
  - Preview reports per date: status create|update|unchanged|stale|invalid, current version,
    period relation, reason requirement, conflict, before and after. It writes nothing.
  - Commit runs in one IMMEDIATE transaction and refuses in this order, all before the first
    write: 409 `stale_version` with `work_dates`; 422 `batch_invalid`; 422 `reason_required`
    when any changed date is in an old or finalized period; 409
    `conflicts_require_confirmation` unless `confirm_conflicts: true`.
  - Unchanged dates write nothing. Each changed entry writes one `day_entry.create|update`
    audit event carrying the reason.
  - Sessions are never touched.
  - Conflict means the date has sessions, the new category is not Worked, and it differs from
    the current effective label. The report counts sessions, clock sessions and open sessions.
  - Other errors: 422 `duplicate_date`; at most 62 entries; strict schema (no `user_id`).

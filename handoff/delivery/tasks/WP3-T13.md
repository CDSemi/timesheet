#### What changed

- **PDF download** (`src/server/routes/submission.ts`): `GET /api/revisions/:id/pdf` through the T13A factory
  (owner = `c.get('subject')`). Owner-scoped lookup (revision, period, ready `revision_files` row, `pdf` attachment);
  another user (admin included) or a malformed id is 404, anonymous 401, not ready 409 `pdf_not_ready`; stored bytes are
  re-checked against the recorded hash (500, never sent on a mismatch); `Content-Type: application/pdf`,
  `Cache-Control: no-store`, `Content-Disposition: attachment; filename="timesheet-<payroll date>-r<n>.pdf"`, nosniff;
  no static path; writes nothing. The factory takes `SubmissionRouterOptions { access?, files? }`; without `files` the
  route is not registered (the T13A tests build the router without a store), the application always passes it.
- **History and delivery** (`HistoryScreen.tsx`, `components/Delivery{History,Revision,Attempts,Confirm}.tsx`,
  `deliveryModel.ts`): revisions per period (current revision from `GET .../finalization`, windows of 182 days from
  `GET /api/periods`, deliveries from `GET /api/deliveries`) with origin and review state as the system records them
  (an automatic submission reads "Submitted automatically" and "Review pending"; "Not signed yet"), PDF download
  (fetch, blob, safe saved name), delivery attempts with state words and the redacted fault code (same rule as the admin
  status), a correction/review link to `#/review/{date}`, explicit resend and the uncertain decision (mark delivered or
  resend), each behind an inline confirmation that takes focus, names the recipients and, for the uncertain resend, the
  double-delivery risk. Refusals (404/409) show their reason and reload; one request at a time.
- **Settings** (`SettingsScreen.tsx`, `components/Submission{Settings,SettingsForm,Preview,ImageOption}.tsx`,
  `settingsModel.ts`): recipients and templates with the server preview (manual or automatic wording), the auto-submit
  switch with its effective rule and the overdue-drafts choice only when the switch changes, the note line (switch,
  default text "Automatic submission", 1-120 characters, one line, validated with the domain rule), the OT-on-PDF switch,
  and the image option as the audited authorization ("Include my signature image on automatic submissions", "Use my
  new image on automatic submissions" when a newer image exists, revoke).
- **Signature upload** (`components/SignatureUpload.tsx`, `api.ts` `uploadSignature`): PNG/JPEG with a data-URL preview
  (the CSP allows `data:` not `blob:`); "Use this image on automatic submissions" is pre-selected (G-Q1 (b)); ticked sends
  `POST /api/signatures?authorize_auto_image=true`, unticked `=false`. Without saved settings a ticked consent is never
  dropped: the upload button waits and a step order is shown (go to the settings, or upload without authorizing). A server
  422 `submission_settings_required` shows "not uploaded and nothing was authorized", keeps the file and the option, and
  re-reads the settings.
- **Grid status** (`components/SubmissionStatus.tsx`, `TimesheetGrid.tsx`, `TimesheetScreen.tsx`): the period's review,
  revision, PDF and delivery state from the finalization and delivery fields, as the grid's table caption on desktop and
  above the day list on a phone, with a link into the history. Attributes `data-grid-status` (not `data-status`) so the
  header badges of T12 keep unique selectors.
- **CSS**: only classes using existing tokens (`code`, history h3, attempt list, confirm panel, grid caption/status).
  No new custom property, no new `@media`, radius and `--transition` reused.

#### Deviations and observations

1. `src/server/app.ts` (not owned): one line, `submissionRoutes(deps, { files })`, so the application passes the private store.
2. `src/client/components/deliveryModel.ts` and `settingsModel.ts` are new files that do not match the owned `Delivery*.tsx`
   / `Submission*.tsx` patterns; they are the modules the owned tests `deliveryModel.test.ts` and `settingsModel.test.ts` import.
3. No server route lists a user's revisions. The history shows the current revision of each finalized period plus any earlier
   revision known through a delivery attempt or the `supersedes_revision_id` of the later one; an earlier revision with no
   attempt that is not a direct predecessor cannot be listed (a read-only list route would close this; out of the owned scope).
4. The e2e harness has no `MAIL_FROM`, so real attempts end `failed_permanent` with a visible fault code; the specs accept
   `accepted` or `failed_permanent` for the first attempt. The uncertain attempt is written into the temporary database by a
   test-only child process (as `seedCredit` does); no production route or flag exists for it.
5. `GET /api/signatures/current` answers 404 for an account without a signature, which the browser logs as a resource error on
   the Settings screen; the existing specs that open Settings tolerate 4xx, mine lists 404 explicitly.
6. `PeriodHeader.tsx` (T12) still shows its own badges; the grid status duplicates them by design (brief item 5).

## Required changes

1. **`cli.js backup --to <dir>`.**
   - It is allowed in production. The target must lie outside `DATA_DIR`; refuse it
     otherwise.
   - It uses the better-sqlite3 online backup API from its own connection.
   - It then runs `PRAGMA integrity_check` and `foreign_key_check` on the copy.
   - It reads the referenced storage keys (attachments) from the copy, copies those
     files, hashes them, and compares each hash with the recorded SHA-256.
2. **The manifest** (`src/server/ops/manifest.ts`).
   - `manifest.json` holds the app version, the schema version, the UTC instant, the
     integrity result, each file's hash and size, and the DB hash.
   - It holds no names, emails or paths of people.
   - The backup is written atomically: into a temporary directory, then renamed.
3. **Status.**
   - Record success or failure and the time in `operations_state`, through migration
     `0009_operations_backup.ts`.
   - `operationsStatus.ts` exposes these fields as data only. The UI comes in WP4-T07.
4. **Consistency, proven by test.**
   - Files are immutable and are renamed into place before their row commits (O7), so
     every key in the snapshot exists.
   - If you choose the brief pause of docs/07:28 instead, it must be a DB-level write
     lock with a bounded timeout. Record your choice and its reason.
5. **Out of scope:** `--prune`. Retention waits for the owner's answer to F-5; do not
   implement pruning in this task.
6. **`scripts/container-drill.mjs`, stage 2.** Run a backup inside the container while
   writes continue, then verify the manifest and hashes outside it.

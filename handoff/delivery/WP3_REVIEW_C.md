  Probe results that establish the scope items:
  - **1 Route inventory.** The 17 shared routes are exactly the auditor's own matrix, derived from WP3-REQ2 item 4. No `ALL` route or middleware sits under `/api/shared`. Under that prefix, 68 non-shared routes were probed for the grantee, a stranger and the admin: 153 probes, all 404 with zero writes. Clock in/out with valid bodies also gave 404. The matrix test pins every one of the 88 entries, so no route escapes it (P5).
  - **2 Live authorization.** One session cookie was kept across every state change. The next request saw each of these: owner revoke 404, grantee leave 404, admin revoke 404, edit→view 403 `grant_scope`, owner deactivation 404 (restored on reactivation), grantee deactivation 401 (sessions revoked; the share applies again after reactivation and a new sign-in). A non-grantee and an admin without a share got 404, an anonymous caller 401, on all 17 routes in all 11 sets, with `no-store`.
  - **3 Items and modes.** For each of the 11 sets, the 17 routes were sent as real requests with valid write bodies. An allowed read gave 200 and wrote nothing. An allowed write gave 200/201 with audit actor = grantee and owner = owner. A refused route gave 403 `grant_scope` with zero changes. The following were all 404 under the share: sign-off, review, finalization, corrections, late review, resend, deliveries and decisions, settings, auto-image, signatures, leave, evidence, history, shares, policy writes and Clock. Another owner's session or revision id through the share gave 404. Re-sharing was impossible (404), and a grantee's own share never reaches the first owner.
  - **4 Race.** Each interleaving was deterministic: the guard admits the request, then a SECOND connection commits the act before the write transaction. The acts were revoke, drop to view, owner deactivation and grantee deactivation; for all 5 write routes the result was 404/403 with nothing written. A revocation in the middle of a download returned no bytes and wrote no audit row. The positive control, the same factory without `shareCheckedDb`, let the write land after the revocation, which proves the window is real. In 20 multi-process rounds (two editor processes and one revoker), no grantee write was committed after the revocation, every 2xx had its audit row, and every request after the first refusal was refused.
  - **5 Attribution.** History shows the grantee's name (never the id) for shared writes, the leave and each `share.pdf_download`. The owner's own download writes nothing. The review hint is missing (WP3-C-01).
  - **6 Records.** Each of these is refused: changing any identity or item column, DELETE, a second revocation, a reason without a revocation, owner = grantee, `created_by` ≠ owner, an empty item set, a non-UTC instant, a second active pair. A change is one transaction: the old row is revoked at the new row's instant, with one `share.change` event carrying both ids. An injected insert failure (a probe-only TEMP trigger) rolled back the revoke. The admin list and revoke responses carry only `id, owner{id,display_name}, grantee{id,display_name}, items, created_at, revoked_at, revoked_by_role`, with no address and no reason. An admin create attempt gets 404.
  - **7 Responses.** No password, hash, token, storage key, address or internal session marker appeared in any shared JSON. `no-store` was present on 200/401/403/404. A second grantee never sees the first grantee. A foreign or missing Origin and `Sec-Fetch-Site: cross-site` give 403. The cookie is HttpOnly and SameSite=Strict. The grantee lookup returns 429 after 10 misses.
  - **8 UI.** In a view-only share, Clock, Edit, batch, selection, review and sign-off controls are absent from the DOM. The only disabled control is "Open day" with an empty date. The day dialog has only Close and no inputs. An edit share has no Clock/review/send control. The OT view has no action control. Without the PDF item the Download button is absent, and nothing is disabled. Every grantee data request went to `/api/shared/<owner>/…` (plus `/api/shares`, `/api/auth/me`). The screenshots were viewed on desktop and mobile.

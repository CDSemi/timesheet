Calendar default under an open editor (owner decision 2026-11-02, R-UX5I2-3; rule: [02 Time and OT](02_TIME_AND_OT_RULES.md) R-03). `PUT /api/days/:date` and each `POST /api/days/batch` entry may carry `default_category`, the calendar default the caller was shown (a category, or `null` for none). The server compares it with the default of the date in the subject's own calendar, read inside the same immediate write transaction as the write. It answers 409 `default_changed` and writes nothing only when all of these hold: the field is present; the date has no entry or its entry's source is `default`; the calendar classifies the date; the field differs from the default now; and the category being saved differs from the default now (when the category equals the new default, both choices record the same category, so nothing is refused). An omitted field is not checked, so a caller that does not know the field behaves as before; an entry whose source is `explicit` is never checked. The PUT body is `{ error: { code: "default_changed", message, details: { work_date, expected_default, current_default } } }`. Order for PUT: the reason rule (old or finalized period), the leave rule, `stale_version`, then `default_changed`; so a day whose entry version moved is answered `stale_version` first, and a day with no entry that gained one meanwhile is `stale_version` too. The batch preview marks such an entry with status `default_changed` (error code `default_changed`, details `expected_default`, `current_default`) after `stale` and `invalid` and before `create`, `update` or `unchanged`, and `can_commit` is false. The batch commit is one transaction and all or nothing; its refusals come in this order: `stale_version` (409), `batch_invalid` (422), `reason_required` (422), `default_changed` (409, details `work_dates` and `changes`, a list of `{ work_date, expected_default, current_default }`), `conflicts_require_confirmation` (409), then the writes. The acknowledgement is the same call with `default_category` equal to `current_default`; a further change refuses again. Nothing is stored for this check and there is no migration; the audit event is unchanged (an update records the effective category before and the person's category after; a create over a date with no entry records before = null). The `default_category` field is optional by decision: an old tab, or a script, that omits it can still overwrite a changed default and is not refused.

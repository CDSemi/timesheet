2. DESIGN CHALLENGE
====================================================================
2.1 "The default the caller was shown". For a no-entry day and a default-sourced entry the form and the cell show day.category, which
    equals day.default_category whenever the latter is not null (timesheets.ts:366, attendance.ts:54). The only difference is a
    default-sourced entry on an unclassifiable date, which cannot occur (C6). So sending day.default_category is equivalent to sending
    the shown category; keep it. The client always knows it: drawer and phone sheet share DayFieldsForm; the shared edit view uses the
    same component with the share's requester; "Open a day" and a day opened from the sheet both load GET /days/:date (DayEditor.tsx:227-240);
    the picker and the batch use the loaded period view (TimesheetScreen.tsx:508-510).
2.2 Mount-time capture versus FIX18/FIX19 (the plan is right; every branch checked):
    - initial load: the form mounts with the loaded day (DayEditor.tsx:570-580, key generation) -> captures the default shown. OK.
    - FIX18 follow taken (sameDayFields true): category equal, so the default is equal for no-entry/default days. OK.
    - FIX18 follow not taken: held day stays, captured default = old = what is shown; the save is refused -> notice (INT3 E3/INT2 E2). OK.
    - FIX19 sameDayFields answer: default equal. OK.
    - FIX19 held branch (dirty): category old, answer's default_category new (C12); the captured default is old -> refused -> notice. OK;
      a live read would pass silently (M10).
    - FIX19 restart branch (nothing typed): new generation -> remount on the answer -> captures the new default the person now sees;
      Save is not refused (E4). OK.
    - Reload day, label/batch refresh (DayEditor.tsx:259-264), period-step epoch (TimesheetScreen.tsx:825): remount -> fresh capture. OK.
    - own successful save: the entry becomes explicit and is never checked again. OK.
    - FIX19 held branch on a NO-ENTRY day after a session create: held entry null, server entry v1 -> stale_version wins (existing
      "Reload day"); the default notice does not appear. Acceptable and consistent with "stale_version first"; state it in docs/04.
2.3 "Use the new default". Nothing is sent. The server already holds the new default (entry absent or 'default'), so with nothing else typed
    the day keeps following the calendar and no save is needed; the plan's status text "Not saved yet." misleads in that case (S3). With
    other fields typed, Save records the new default as the person's explicit choice with those fields (existing rule, hint at
    DayFieldsForm.tsx:140-143). The editor re-read: acceptable but must be specified tightly (S4) and the sheet behind must be refreshed
    (onChanged), else the cell keeps the old default and a later pick on it is refused again (S5).
2.4 "Save anyway". Resend = the CURRENT draft (the person may have typed after the notice), the live entry version, the reason, and
    default_category = current_default from the 409. A second change in between -> 409 again with the newer default (correct, I3/W12).
    stale_version -> the default notice must close and the stale notice show (S6). The button must be disabled while busy or while the
    reason is missing, like "Save day fields" (DayFieldsForm.tsx:105) (S7). Focus after success: the clicked button disappears with the
    notice, so focus would drop to the body (the R-UX5I3-3 class); move it to the Category select (S8).
2.5 Check order and concurrency. PUT: imported 409 / reason 422 (prepareEdit) -> leave 422 -> stale_version 409 -> default_changed 409
    -> write. Agree with the plan. Batch commit is not specified by the plan; specify: stale_version -> batch_invalid -> reason_required ->
    default_changed -> conflicts_require_confirmation -> writes (default before the conflict step, so nobody confirms a conflict and
    then learns that the default moved). Concurrency: both sides IMMEDIATE, scope read inside (C10): no window. Error shape:
    {error:{code,message,details}} like the other 409s (errors.ts:29-33).
2.6 MF1 - false notice when the person's category already equals the new default. The plan refuses whenever sent default != current.
    Cases: (a) the person selects Holiday themselves while the admin imports the holiday; (b) after the notice the person selects the new
    default in the select and presses "Save day fields" (the form still sends the old captured default -> refused again, a loop until a
    notice button is used); (c) a pick of "Holiday" on a stale cell whose default became Holiday -> review dialog "changed elsewhere,
    reload". In all three both of the owner's choices give the same category, so there is no decision to make. Rule: refuse only when
    input.category != current. Nothing the owner protects is lost: the person records exactly the category the calendar now gives.
2.7 MF2 - the picker and the batch. A pick always previews first (TimesheetScreen.tsx:517-526); with a stale sheet the preview, not the
    commit, carries default_changed, opens the review dialog with can_commit false and the text "Close this window and reload the
    period" (BatchDialog.tsx:97-101). Closing it only clears the preview (:534-538): no "Reload period" control appears (it exists only
    for a commit 409, :482-484 and :766-772), and the own view reloads the period only on a clock-version change (:311-316); a shared view
    never does. A second pick sends the same old default and is refused again. So neither of the owner's choices is reachable in the app
    (only a browser reload or a period step). Fix: when a preview holds stale or default_changed entries, closing the review dialog sets
    the page's stale notice with those dates (staleReloadMessage, dayModel.ts:141-144), so "Reload period" is offered; reload then shows
    the new default (= use it) and a new pick saves over it (= overwrite, now seen). This also closes the same gap for 'stale', a benefit.
    The dialog row should name the new default (S9).
2.8 False notices otherwise. Time zones (AGENTS rule 7): the check uses the explicit accounting date and the owner's calendar; neither the
    device zone nor the display zone enters (DayEditor workDate, timesheetCommands.ts:423). A version created for other dates or a
    rename: the comparison is by category, so no notice (keep I5, add a rename). A no-change import writes no version
    (holidayImport.ts:352). Remaining false notice: MF1 only.
2.9 Accessibility and UI. Focus-moved role="alert" container with tabIndex -1 has an in-repo precedent (ReviewScreen.tsx:290, a .stale box
    with buttons), so the plan's announcement/focus choice is consistent; prefer the .stale component (styles.css:2511-2525, the same
    look as "Reload day" in this editor) over .warn-box (styles.css:4063, a <p> block) for a box that holds buttons (S10). Buttons: the
    generic touch rule gives 44px below 768px and with a coarse pointer (styles.css:791-796 comment); they must not use .editor-actions
    (36px visible box, styles.css:3895-3916). Colour: --warn exists in all theme sets; words carry the state. U4-05 unaffected (a refusal
    changes no draft).

 - current = calendar default of the date in the SUBJECT's scope (new helper calendarDefaultOn(scope, date): DayCategory | null in

 - Refuse iff: the field is present AND (no entry OR entry.category_source = 'default') AND current != null AND sent != current AND
   input.category != current. Explicit entries and an omitted field are never checked.

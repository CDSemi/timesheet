1. MECHANISM (how the save works today and why a changed default is not seen)
====================================================================
What the client sends. DayFieldsForm.save (src/client/components/DayFieldsForm.tsx:81-102) calls buildDayEntryRequest
(src/client/components/sessionModel.ts:458-473) and PUTs /days/:date with { category, leave_minutes, leave_kind, wfh, notes,
expected_version = day.entry?.version ?? null, reason? }. It sends no category source and no default. The schema is strict
(src/server/http/schemas.ts:86-96, dayEntryBody). The label picker and "Change several days" send one POST /days/batch entry per date
{ work_date, category, expected_version = day.entry?.version ?? null, ... } (labelPickerModel.ts:44-49, dayModel.ts:115-119,
TimesheetScreen.tsx:442-532).

What the server checks. applyDayEntryChange (src/server/services/timesheetCommands.ts:328-420), shared by PUT /days/:date and the batch commit:
reason rule (prepareEdit), leave rule (dayEntryIssue), then only the entry version:
  - no entry for the date: expected_version must be null (line 341), then INSERT with category_source 'explicit' (350);
  - an entry: expected_version must equal its version (380), then UPDATE with category_source = 'explicit' (393).
The batch plans the same test in planBatch (src/server/services/dayEntries.ts:123).
Nothing compares the category the person saw with the calendar default now.

Why a changed default is invisible. A default-sourced entry stores a category but the shown category is derived from the calendar at read time
(effectiveCategory, timesheets.ts:247-255; buildDayView :365-366; resolveDayCategory, domain/attendance.ts:49-55). The only runtime writer of
a default is the administrator's holiday import: createCalendarVersion (calendars.ts:158-205) inserts a calendar_versions row and an audit event;
it writes no day_entries row (by design: docs/10 E-4 and F-2 (b), docs/03 "Records" exception). So the entry version does not move, and a
day with no entry has no version at all. The version guard therefore cannot see the change.

The three cases:
  A. Day with no entry. Client holds expected_version null and the shown default (say Worked). Import makes the default Holiday.
     Save sends Worked, null. Server: no entry -> version null accepted -> INSERT explicit Worked. Silent overwrite. (INT2 E2)
  B. Entry whose category_source is 'default' (created by a Check in or a session write). Client holds version v and the shown
     default. Import changes the default. Save sends the old category with v. Server: v matches -> UPDATE explicit Worked. Silent
     overwrite. (INT3 E3; observation 46-obs-int3-admin-target.txt: "after the import the server says Holiday/default entry v1 ...
     Save day fields: ACCEPTED; server category Worked/explicit ... entry v2")
  C. Entry whose category_source is 'explicit' (the person's choice). The import does not touch it and the form shows the person's
     category; nothing is overwritten that the person did not choose. No problem, no notice needed.
Consequence (obs, INT3): a holiday recorded as Worked makes the day owe required time (attendance_expected true, deficit). With nothing
typed, FIX19's session-write path restarts the form on the new default (E4: shows Holiday), so E4 is already safe; the open risk is a
typed edit (held branch, E3), the tab-return path, the phone sheet and the no-entry day (E2).

2. SCOPE: "the default changed"
====================================================================
Write paths that can record a category over a default (all must be covered, because they all reach one of two server functions):
  P1 Day editor, desktop drawer: PUT /days/:date from DayFieldsForm. IN.
  P2 Day editor, phone bottom sheet: the same component and route (foot Save button). IN, same code.
  P3 Shared edit view (a grantee editing for an owner): the same DayEditor with request = the share's route set, same service
     function, subject = owner. IN, by the server check; no extra client code.
  P4 In-cell label picker: one-entry POST /days/batch (preview, then commit). IN.
  P5 "Change several days": POST /days/batch with many entries. IN.
  P6 Check in / Check out / session create, edit, delete: ensureDayEntry (timesheetCommands.ts:149-170) creates a default-sourced row; it
     records the calendar default as a default, never a category over one. OUT.
  P7 Workbook import (workbookImport.ts:681): the person's own deliberate import of finished periods, previewed, read-only history. OUT.
  P8 Seed and bootstrap. OUT.
Events that change a default:
  E1 Holiday CSV import commit (admin): adds, removes or changes the kind of a holiday or closure (holidayImport.ts:353). IN. The only
     runtime event; createCalendarVersion has three callers (holidayImport, bootstrap:213, seed:254).
  E2 Calendar edit: no other route exists. Nothing more to cover.
  E3 Calendar assignment: refused with 409 calendar_in_use once the account has data (users.ts:177-183). A reassignment of an account
     with no data would also change a no-entry day's default; the server compares against the owner's current calendar, so it is covered
     automatically by the same check.
  E4 Work-policy change: defaultCategory depends only on the calendar classification (domain/attendance.ts:17-28); a policy change moves
     figures but not the category default. OUT.
The rule: "a write that would record a category over a calendar default, when that default is different from the one the person saw."
It applies only where a default is at stake: no entry, or an entry with category_source 'default'. An explicit entry is the person's own and
never follows the calendar (case C), so it is never checked.

3. DESIGN
====================================================================
3.1 Chosen design A: the client names the default it showed; the server refuses a mismatch; the Day editor offers two choices.
  API contract (backwards compatible, no migration, nothing stored):
    - PUT /api/days/:date body and each POST /api/days/batch entry gain  default_category?: Worked|Off|Vacation|Sick|Holiday|Shutdown|null
      ("the calendar default the caller was shown"; null = the caller was shown none). Strict schema stays strict (schemas.ts:86-96, 106-115).
    - Server rule, after the reason rule and the existing version check (so stale_version always wins), inside the same IMMEDIATE
      transaction as the write:
        current = calendar default of the date for the OWNER's calendar (null when the calendar cannot classify the date)
        if (entry is absent OR entry.category_source === 'default')
           AND body.default_category !== undefined AND current !== null AND body.default_category !== current
        then refuse, write nothing.
    - PUT answer: 409, code "default_changed", message
        "The calendar default for {date} changed from {expected} to {current} since it was loaded. Nothing was saved."
      details { work_date, expected_default, current_default }.
    - Batch: preview marks the entry status 'default_changed' (new value beside create/update/unchanged/stale/invalid) and can_commit is
      false (like stale); commit answers 409 "default_changed" with details { work_dates: [...], changes: [{work_date, expected_default,
      current_default}] }, all or nothing, and stale_version for any date still wins.
    - Acknowledgement is the same call repeated with default_category = current_default; no new flag. A second change in between
      refuses again.
    - Audit: unchanged. The update event already records before = effective category (Holiday) and after = the person's category, so an
      acknowledged overwrite stays traceable.
  Client:
    - DayFieldsForm captures the default it was seeded with when it mounts (state shownDefault = day.default_category) and sends it on every
      save. It must not read the live prop: the FIX19 held branch (withHeldDayFields, DayEditor.tsx:49-59) keeps the old category and entry
      under an answer whose default_category is already new; a live read would send the new default under the old category and silently
      pass. (This is mutant C1.)
    - On 409 default_changed (validated shape; otherwise fall back to the existing generic error) the form shows the notice and keeps
      every typed field.
    - The notice, English UI, placed inside the "Category and leave" form directly under the heading and above the OT-mismatch box and
      the fields (same slot on the 400px drawer and on the phone's sheet body; the fields it concerns are right below it):
        [warn-box, role="alert", tabIndex -1, focus moves to it; scrollIntoView({block:'nearest'}) so the phone's foot Save does not hide it]
        "Notice. The calendar default for this day changed from Worked to Holiday since it was loaded. Nothing was saved."
        "Use the new default, or save your category over it."
        Buttons in this Tab order (the safe, non-writing one first):
          "Use Holiday"            (secondary)
          "Save Worked anyway"     (primary; Worked = the category typed in the form now)
      Styling: the existing .warn-box tokens (--warn text, --elev-1, --radius) and the existing .button-row; no new custom property, so no
      new dark-set value. The state is carried by the words "Notice." and the names of the categories, not by colour. Below 768px and with a
      coarse pointer both buttons are the existing 44px targets with the shared focus ring. If the worker needs a rule it goes through a
      custom property in the light set and both dark sets (AGENTS UI standard 1) and cssThemeParity.test.ts / styleTokens.test.ts cover it.
    - "Save Worked anyway": sets shownDefault = current_default, repeats the save with exactly the typed fields and
      default_category = current_default. On success the usual onSaved ("Day fields saved.") runs and the notice goes. A refusal again
      (another change) shows the new notice; a stale_version goes to the existing stale notice.
    - "Use Holiday": nothing is sent. The Category select takes the new default; the notes, WFH, partial leave and kind keep what was
      typed (decision: the owner's "update" refers to the default value, so only the category follows it). shownDefault = current_default;
      the form's baseline is rebased so that taking the default alone is not an unsaved edit (a note typed before still is); the notice
      closes; a polite status line "Category set to Holiday, the new calendar default. Not saved yet." is added to the form; focus goes to
      the Category select. The existing hint "Calendar default. Saving records it as your choice." stays true and visible.
      DayEditor is told (onDefaultTaken) and reads the day once: if it differs from the held day only in the default-derived category
      (same source 'default', same leave, kind, WFH and notes) it takes the answer without a new generation, so chips, banner and figures show
      the Holiday day; otherwise it raises the existing stale notice ("Reload day"). A failed read changes nothing. The read uses the dayStamp
      guard of the follow effect.
    - Batch and label picker (P4, P5): the model functions add default_category: day.default_category to each entry. A preview with
      'default_changed' opens the existing review dialog, which already says "Some dates changed elsewhere or are not valid. Close this
      window and reload the period." (STATUS_TEXT gets 'calendar default changed'); a commit refusal 409 default_changed is handled as
      stale_version is (TimesheetScreen.tsx:482-484): the page shows staleReloadMessage(dates), "{dates} changed since this period was
      loaded. Nothing was saved. Reload the period, review the new categories and try again." The two choices exist there as the page's
      own flow: reload (= use the new default, the cell now shows it) or pick again on the reloaded sheet (= save over it, now seen). No
      new dialog. This is a scope reading, see the Question list item 1.
  Fit with existing rules:
    - Stale notice: version mismatch is answered first (stale_version -> "Reload day"), so the two notices never compete; a default
      notice is cleared whenever the form remounts (Reload day, a restart after a session write, a label or batch reload).
    - U4-05 unsaved-changes guard: unchanged. A refusal changes no draft, so the form stays dirty and Close, Escape, another day and
      Next period still ask "Discard your changes?". After "Use", dirtiness reflects only what the person typed.
    - FIX18 follow: sameDayFields (DayEditor.tsx:33-42) already differs on the category of a default-sourced entry, so a tab-return read
      is not taken (the held day stays) and the later Save is now refused with the notice instead of overwriting (INT3 E3). No change to
      the follow effect.
    - FIX19 held branch (withHeldDayFields): unchanged in code; it is the reason the form captures its own default (above). The
      restart branch (nothing typed) re-seeds the form from the answer including its new default, so E4 shows Holiday and Save raises
      no notice. Correct: the person saw the new default.
    - Phone sheet: Save lives in the foot; the notice sits at the top of the scrolling body and is scrolled into view and focused on
      appearance; pressing Save again while it is open simply raises it again.
    - Shared edit view: identical component and server path.
3.2 Alternatives compared.
  B. A calendar revision token (send day.classification.calendar_version_id and compare). Rejected: classifyDate returns the id of the
     version effective on the date (domain/calendar.ts:63-79); every import creates a new version, so every date from its effective_from on
     gets a new id and every open default day would be refused although its category did not change (a false notice on each import).
  C. Proactive detection only on the client (the tab-return/follow read compares the category and raises the notice before any save).
     Rejected as the only mechanism: it needs a read to happen (never on the phone sheet, never without a tab event) and cannot cover
     label picker/batch; the server must refuse anyway. It can be added later on top of A without contract change.
  D. Option (b) of the review (send the category only when changed) or plain refusal (c). The owner chose a notice with two choices, which A
     implements; (b) alone would still need a rule for a typed note on a changed default.
  A is the smallest design that is complete: one optional field, one check in the two shared server functions, one notice.

4. SERVER-SIDE SAFETY
====================================================================
  - The check lives in applyDayEntryChange and planBatch, inside the IMMEDIATE write transaction, against the owner's scope
    (loadScope(ctx.user), where user = the subject), so a concurrent holiday import (also a write transaction) is serialised with it.
    Ownership is unchanged; the 409 details hold only the caller's own date and two category names.
  - Shared helper (new, one place): calendarDefaultOn(scope, date): DayCategory | null in timesheets.ts, which effectiveCategory and
    dayEntries.currentCategoryOf (dayEntries.ts:90-98) also use (removes two copies of the try/classify/catch block).
  - No check when current is null (the calendar cannot classify the date: nothing to protect). No check for explicit entries.
  - A stale client that does not send the field (an old tab still holding the previous bundle after a deploy, or a script): not checked,
    exactly as today. DECISION AND REASON: the field stays optional. Making it required fails closed but would break every caller that
    creates an entry without a default (77 PUT call sites in tests/ across 22 files, helper bodies in each file, plus tests/e2e/fixtures.ts
    and the share/auth matrices) for a risk with three conditions at once: a deployed bundle change while a tab is open, an
    administrator's default change on that very date in the same window, and a save by that tab. The client ships in the same image as
    the server, the overwrite is visible on the sheet, recorded by the audit event (before = Holiday, after = Worked) and corrected by
    one more edit. A strict variant is costed in the Questions list, item 2, for the coordinator to veto. The contract text (docs/03)
    says "an omitted field is not checked".
  - No migration: nothing is stored. dist/server changes (schemas.ts, timesheets.ts, timesheetCommands.ts, dayEntries.ts), so the gate
    reruns the container drill (--wp3, every stage) and "npm audit --omit=dev"; package.json and the lockfile do not change.

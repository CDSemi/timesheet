Observations.
  1. Idle, every test is far below 30 s, but in the full parallel run the suite slows itself: deadline-race 4.1 s alone -> 12.6-15.8 s in the full run (3-4x), backup-prune 3.6 -> 6.2-12.4 s, restore 3.3 -> 5.5-11.6 s. The run-to-run spread at idle is already 2x (12.6 vs 15.2 s). The margin to 30 s is 2x for deadline-race.
  2. Neither CPU load alone (burner on all 32 logical cores) nor file churn reproduced a failure (55 s, 62 s). The Windows scheduler gives the short test processes a fair share.
  3. Giving the suite fewer logical CPUs while vitest still runs its default 31 forks does reproduce the FIX5 failures: 8 CPUs -> 3 failures, 4 CPUs -> 6, 2 CPUs -> the same set FIX5 saw (backup, backup-prune, jobs-restart, restore, deadline-race; FIX5 npm test run 1 took 272 s and run 2 115 s against 48 s idle). So FIX5's host offered the suite roughly 2-4 CPUs' worth of capacity for a few minutes. What took the capacity was not running at either census (about 1.5 to 4 cores busy; 10-census.txt) and is not identified. The 45 msedge processes FIX5 saw are the owner's Edge (one parent, started days ago); they used 0.07 core at the first census and 2 cores at the second, so they can add a little load but not 28 cores' worth.
  4. Self-contention is the lever that is ours: with the same 4 logical CPUs, 16 workers (not 31) took 130 s instead of 139 s, with 0 failures instead of 6, and cut the slowest test of the sensitive files by 25-45% (deadline-race 30.7 -> 15.6 s, restore 14.5 -> 8.1 s). 8 workers: 126 s, slowest 12.6 s. On the idle host 16 workers cost nothing (53 s against 48-53 s) and 8 workers cost +60% (81 s). 31 forks, each also spawning CLI children, oversubscribe the 16 physical cores / 32 SMT threads.
  5. Cheaper spawns (lazy PDF library, 20-cli-cost.txt) take 37% off each CLI: 4 CPUs/16 workers backup-prune 14.9 -> 8.8 s, bootstrap 5.9 -> 2.4 s, restore 8.1 -> 5.3 s, deadline-race 15.6 -> 10.6 s; idle full run 43 s with the config change and the lazy import together. The remaining load-sensitive tests that no spawn cost explains are in-process CPU work: deadline-race (worker threads), pdf-render (30 s), workbook-reader (time-bound assertions 5000 / 2000 ms inside the test, tests/integration/workbook-reader.test.ts; they fail at 4 CPUs with 31 workers and pass with 16; do not loosen them).
  6. Limit of the fix: at 2 logical CPUs (16x fewer than the 32 vitest sees) even 16 workers and lazy import fail (slowest 39.8 s). Between 4 and 2 CPUs the margin is exhausted; no setting can make a host that gives away 94% of its CPU to something else pass a 30 s limit. That regime must be avoided at the gate (run only when the census shows a quiet host) and the failing run repeated once.
  7. Dropbox path versus export: single CLI +25 to +45% (20-cli-cost.txt); full suite 53 s (repo) against 48-49 s (export), about +10%, inside the run-to-run spread. The repository path is not the cause of the timeouts.
  8. Not shown to matter: database and file I/O (a spawned command's database work is tens of ms; 1.0 M small files of churn changed nothing).

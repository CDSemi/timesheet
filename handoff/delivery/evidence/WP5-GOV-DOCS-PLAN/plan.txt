1. WHAT COUNTS AS DOCUMENTATION (exact path rule)
======================================================================
A path (as printed by git, relative to the repository root, outside handoff/) is DOCUMENTATION when ALL hold:
  - it ends in `.md` (so every `.vi.md` too);
  - it does not start with `src/`, `tests/`, `scripts/`, `assets/`, `.claude/`, `.agents/` or `handoff/`;
  - it is not absolute and has no `..` part.
Result: AGENTS.md, CLAUDE.md, DEVELOPMENT.md, README.md, docs/*.md, docs/adr/*.md, docs/agents/*.md,
reference/**/README*.md and their .vi.md pairs. handoff/ is documentation or state by nature but never needs the
rule (the digest excludes it). Everything else is NOT documentation: code, tests, scripts, package.json and
lockfile, tsconfig/vite/vitest/playwright/eslint config, Dockerfile, .dockerignore, compose.example.yaml,
.env.example, .github/**, ingat.toml, skills-lock.json, .gitattributes/.editorconfig, JSON fixtures, the workbook,
the font and OFL.txt, agent profiles and skills.
Correction to the coordinator's starting proposal: add `assets/` to the excluded roots, because
assets/pdf-fonts/README.md is read and asserted by a test (O7) and sits in the Docker allow-list; its
README.vi.md goes with it. Confirmed: every other proposed inclusion/exclusion matches the repository.
Non-.md files stay non-documentation on purpose (conservative; no file of that kind is documentation today).
Governance Markdown (AGENTS, CLAUDE, docs/08, docs/agents, and handoff/prompts|templates which are outside the
digest) is documentation BY PATH (so its commit does not break a WP acceptance) but a RULE change in it is not
documentation-only - see section 2.

2. THE REVIEW-AND-FIX PROCESS
======================================================================
Who: author = worker (medium, sonnet). Reviewer-fixer = a different, fresh worker instance (medium, sonnet; the
profile is worker-high, sonnet, when the change restates acceptance or status facts across many files or edits
documents 01-05 and 07). The reviewer may edit the same paths; it is not an auditor and no verifier gate or
freeze commit exists. The reviewer's agent_id must differ from the author's agent_id and previous_agent_ids.
Checks (all by reading, plus the existing aids):
  a. currency: every factual statement the change touches or cites (status, counts, SHAs, task IDs, file and
     command names, ports, versions) against the code, the board, STATE and the records it names;
  b. cross-document consistency: other documents that state the same fact (README, DEVELOPMENT, docs/12,
     WP5 handoff, pilot packet, runbook);
  c. EN/VI parity: same meaning, same IDs; `python handoff/delivery/validate_package.py --preflight` as an aid;
  d. links and cited names: preflight resolves links; the reviewer also greps src/ and tests/ comments before a
     document heading, section name or ID is renamed or removed (O7: they cite "docs/03 'Records'" etc.);
  e. no private data (AGENTS rule 4) - read the diff;
  f. BUSINESS/WORKFLOW-RULE SAFEGUARD (below).
Records: the reviewer appends to its task Results (English): facts checked, drifts fixed (file:line), preflight
exit, "rule_change: none". No new template; one bullet is added to TASK.md.
Commit: timesheet-committer, one documentation commit, no freeze. Its normal checks stay (precommit-check,
`git diff --cached --check`, JSON parse, orchestration validator when the board is staged, diff read for personal
data) and it adds `validate_orchestration.py --documentation-staged` (section 5) before committing and
`--documentation-range <accepted>..HEAD` after. Message body: `Task: <id>` and `Gate: none (documentation)`.
Safeguard (rule): a change is NOT documentation-only when it adds, removes or alters
  (i)  a behaviour a correct implementation must satisfy (documents 01, 02, 03, 04, 05, 07; acceptance criteria
       in 06; AGENTS rule 8), or
  (ii) an obligation, permission, role, gate, limit, path list or validator assumption of this workflow
       (AGENTS.md, CLAUDE.md, document 08, handoff/prompts, handoff/templates, docs/agents).
Test: "would a correct implementation, or a correct run of the workflow, of the OLD text now be wrong?" If yes, or
if the reviewer is unsure, it is not documentation-only: (i) is planned as a code task whose freeze, gate and
audit stay (the text ships with that task); (ii) keeps the GOV freeze commit, gate and fresh audit. Wording,
currency, link, translation and status fixes in those same files that change no rule ARE documentation.
Mechanical backstop: validator-checked attestation `rule_change` on the board record (section 3); the range
listing proves no non-Markdown file changed; the next code audit reads the documents against the code anyway.

3. ACCEPTANCE AND RELEASE IDENTITY AFTER A DOCUMENTATION-ONLY COMMIT
======================================================================
Options compared
(a) Keep `npm run digest` unchanged. The board records the documentation-only successors of the current
    acceptance; the validator accepts an audit PASS whose reviewed_digest is the recorded base while
    current_source_digest is the recorded head; git proves the paths.
      + No recorded digest changes meaning (559 tasks, hundreds of gate/audit records, D_PRE ls-tree forms in
        briefs and evidence stay reproducible).
      + ~45 lines of Python in handoff/ (a governance path, so one GOV cycle) and about 17 in-memory probes.
      + Code files keep their identity rule exactly; any non-documentation path ends the record (stale PASS as today).
      - The record is bookkeeping the coordinator must keep (the validator forces it: a mismatch is "Stale PASS").
(b) Make the digest exclude documentation.
      - Changes the meaning of every recorded digest: `npm run digest` at any old commit no longer reproduces the
        recorded value, so history cannot be re-verified; the ls-tree one-liner in scripts/source-digest.mjs,
        briefs, DEVELOPMENT.md and committer evidence must change too.
      - The path rule would live in JS and Python, or a second digest would be needed (a new concept).
      - scripts/ is code: it needs a full gate and audit of its own.
      - A documentation commit would not change the digest, so the commit SHA alone would still be needed to name the release.
(c) Validator runs `git diff` live to compare the audited commit with HEAD.
      - Needs git history in every checkout (scratch clone, export) and breaks the "synthetic in-memory" probes.
RECOMMENDATION: (a), with git used only in an explicit CLI mode (independent proof), not inside validate().
Why: smallest change, no meaning change, probe-able, honest about what is proven by what.

Board record (new optional top-level key; absent means none):

  V1  is_documentation(path) as in section 1; every path must satisfy it; paths nonempty, unique.
  V2  base_commit/head_commit/reviews[].commit are 40-hex; base_digest/head_digest are 64-hex and differ.
  V3  reviews nonempty. author_task: a done task of kind documentation, implement or fix. review_task: a done task
      with an agent_id. rule_change "none" -> review_task kind documentation; rule_change "audited" -> review_task

  V6  stale-PASS check (line 318) becomes: reviewed_digest == current_source_digest OR (record present AND
      reviewed_digest == record.base_digest AND current_source_digest == record.head_digest). Message unchanged
      ("Stale PASS: <id>"), so the existing probes still match.
  The next code acceptance (a new gate and audit at a new digest) replaces the record: the coordinator deletes it;
  V4 fails on a leftover record whose base no longer has a current PASS.

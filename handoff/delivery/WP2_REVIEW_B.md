- Findings: severity | file/function | reproduction | expected/actual | rule/AC | bounded fix:

  **WP2-B-01 — Medium — manual-entry input zone defaults to the reporting zone, not the current display zone.**
  - File/function: `src/client/DayEditor.tsx:75` builds `zones = [reportingZone, displayZone, ...COMMON_ZONES]`; `src/client/components/SessionForm.tsx:53` uses `zones[0]` as the default input zone of a new session. The e2e pins the behaviour: `tests/e2e/day-editor.spec.ts:95` expects `America/Los_Angeles` while the browser zone is Asia/Ho_Chi_Minh. The T10 record states the choice ("default: the reporting zone, never the device zone", `tasks/WP2-T10.md:127`); no decision record changes R-07.
  - Reproduction: browser zone Asia/Ho_Chi_Minh, Day editor, Add session. The Input zone field shows America/Los_Angeles while the editor text says times are shown in Asia/Saigon and the session list displays Saigon times (`input-zone-default-desktop-synthetic.png`, `audit-b-input-zone-*.json`, both projects).
  - Expected/actual: R-07 (docs/02 line 74, same in the .vi.md): "Manual time entry must show and use its selected input zone, defaulting to the current display zone". The display zone is the device/current zone (docs/04 settings table), and the shell already uses it for Clock in (`TimesheetScreen.tsx:118`). Actual: the reporting zone is the default. A user away from Los Angeles who types local wall times and keeps the default stores instants several hours off; they then fail `future_time`, or land as wrong intervals within the one-day `work_date` tolerance. That gives wrong raw and OT figures. The zone is visible and editable, which limits the risk.
  - Rule/AC: R-07; AGENTS rules 7 and 8 (rule 7 does not require this default: the accounting date is explicit, so a display-zone default regroups nothing; rule 8 forbids a silent change of a canonical behaviour).
  - Bounded fix: make the current display zone the first and default input zone (for example `[displayZone, reportingZone, ...COMMON_ZONES]`, or an explicit `defaultZone` prop). An edited session keeps its saved `input_zone`. Update `day-editor.spec.ts`: assert the display-zone default, and set the zone explicitly in the tests that type Los Angeles wall times. Server unchanged. Recheck: e2e on both projects plus `npm run verify`. If the owner prefers the reporting-zone default, the alternative is an owner decision that amends R-07 in docs/02 and .vi.md with a docs/10 entry, followed by a recheck of the docs only.

  **WP2-B-02 — Low — new literal style values instead of CSS custom properties.**
  - File: `src/client/styles.css`. Literal heading sizes added in WP2: `font-size: 1.1rem` (line 632), `1.05rem` (825) and `1.3rem` (843). Literal layout widths: `minmax(11rem, 1fr)` (410), `min-width: 10rem` (587), `min(36rem, 92vw)` (616), `min(56rem, 96vw)` (678), `minmax(9rem, 1fr)` (802), `minmax(6rem, 1fr)` (876) and `minmax(14rem, 1fr)` (966). The documented breakpoint literal (767/768 px; custom properties cannot drive media queries) and the 1–2 px hairlines are accepted.
  - Expected/actual: AGENTS.md "Unified Frontend & UI/UX Standards" step 1: "Never introduce arbitrary styling; introduce new values only as CSS custom properties". Colours, spacing, radius, shadows and transitions are tokenized (verified), but these sizes are not.
  - Rule: AGENTS UI pre-flight (E-8 visual standard, docs/04 "Visual standard").
  - Bounded fix: add tokens to `:root` (for example `--font-size-md`, `--font-size-lg`, `--font-size-xl`, `--dialog-width`, `--dialog-width-wide`, `--field-min`) and reference them, with no visual change. Recheck: `npm run verify`, the e2e suite and one screenshot per screen.

R-07 prefers the display zone, so consider showing it there (it fits with the WP2-B-01 fix) and labelling it as derived.

  7. The `policies.ts` ↔ `timesheets.ts` import cycle is function-level only: there is no top-level use of an imported binding, and it works under Node 24 ESM. This is acceptable; a later refactor could move `listPolicyVersions`/`PolicyVersion` into a third module.

  9. Admin-created accounts have no work policy until the user creates one in Settings, so every day shows "policy missing" (`isolation-employee2` screenshots). The owner may want a starter policy on creation.
  10. The mobile 44 px target assertions exist only in the shell, timesheet and day-editor specs. This audit's probe found OT, History, Settings and Admin compliant on mobile (0 small targets, 0 overflow). Adding them to the specs would keep it so.
  11. Design notes judged acceptable:

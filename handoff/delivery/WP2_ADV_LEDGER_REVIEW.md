- Findings: severity | file/function | reproduction | expected/actual | rule/AC | bounded fix:
  - **ADV-A-01 | Low | `src/server/services/ledger.ts:344-354`, `postCorrection` duplicate branch.** Reproduction: post credit 60, then correction with key K to 90 (+30), then the same key K with corrected value 120 (`05-probe-negative.txt` P5.1). Expected, per the service's own contract (`ledger.ts:20-22`) and like `postCredit`/`postDeficitDebit`: 409 `source_key_conflict`. Actual: status `duplicate`, delta +30; the caller asked for 120 and gets 90 with no error. Nothing is appended, so LG-01 and the fixture rule still hold. Rule: R-06 unique source-event keys. Fix: in the duplicate branch, compute the magnitude implied at the existing entry (original plus corrections up to and including it) and throw `source_key_conflict` when it differs from `correctedMinutes`; add a test.
  - **ADV-A-02 | Low (decision needed) | `src/server/services/ledger.ts:356-391`, `postCorrection` on a `deficit_debit`.** Reproduction: posted 60, debit 60, correction of that debit to 90 (P5.3). Expected under R-05: a proposed debit that the available balance cannot cover stays pending, never negative. R-06 allows a negative result for a "truthful correction" of a posted credit. Actual: −30 is posted, the balance becomes −30 and is flagged. A debit increase bypasses the `canDebit` check that `postDeficitDebit` applies. Rule: R-05, R-06. Fix: apply `canDebit(available, increase)` to debit-increasing corrections and return a pending result with no entry when short. Alternatively, record a canonical decision in docs/02 R-05/R-06 (+ .vi) that debit corrections may go negative and are flagged. Add a test either way, before WP3 uses corrections.
  - **ADV-A-03 | Low | `src/server/services/otLeave.ts:607-613`, `cancelOtLeave`.** Reproduction: reserve 120 (version 1); record use 120 (version 2); cancel with `expected_version: 1` over HTTP (`07-probe-stale-cancel.txt`; also 1 of 20 rounds in `06a`). Expected: 409 `stale_version`, as the route requires `expected_version` and the same stale cancel after partial use returns 409. Actual: 200 `unchanged`, released 0, because the no-op branch returns before `checkVersion`. Data stays consistent. Rule: docs/03 "validate ownership/version on each action". Fix: check the version before the no-op branch, or document that cancel is version-free when nothing is reserved and have the client treat `unchanged` with a newer version as changed elsewhere. Add a stale-cancel test, and pass `expectedVersion` in the cancel-versus-use race.
  - **ADV-A-04 | Low (privacy metadata) | `src/server/services/history.ts:60-63, 82`, `getHistory` cursor.** Reproduction: employee events, then 7 admin logins, then an employee event; employee pages `GET /api/history?limit=1` (`09-probe-history-cursor.txt`). Expected: own events only, nothing about other people. Actual: `next_before` is the global `audit_events` rowid, so the gap between consecutive own cursors (16 to 8) shows that 7 other audit events happened in between. With `occurred_at`, this reveals colleagues' activity volume and timing. No identifier or content leaks. Rule: AC-01 / E-13 "own events only". Fix: use a cursor that carries no global sequence, such as a keyset on the user's own (`occurred_at`, `id`) or an opaque per-user token. Add a test that the cursor reveals nothing about other users' event counts.
  - **ADV-A-05 | Info | `src/server/services/otLeave.ts:220-237, 372-422`, `appendLeaveEntry`/`toEntry`.** These duplicate `ledger.ts:143-160, 243-292` (INSERT, row mapping, audit). It is not a defect today, but a future invariant added to `appendEntry` would be bypassed by leave postings. Optional: export one internal append function from `ledger.ts` and use it in both places.
- Verified behaviour (no defect found):
  - T02. Append-only ledger: UPDATE and DELETE are rejected (P4.1). Per-user unique `source_key`; sign CHECKs per entry type; a correction targets only the same owner's original credit or debit (P4.3, trigger). Leave counters are forward-only with `approved = reserved + consumed + released` and `reversed ≤ consumed`. Permission facts are immutable, and every update must bump the version by 1 (P3.7, P4.2). Posted = sum of deltas and available = posted − reserved, both from the pure engine. LG-01 duplicate, LG-02 +30, LG-08 −60 kept and flagged, LG-09 `unchanged`, and the R-05 pending debit (no entry, P5.4) are covered by passing tests and probes. Savepoint rollback inside a caller's transaction is tested. The WP1 upgrade built with f32978f code applies [2], leaves all 12 WP1 tables byte-identical and passes integrity and FK checks. WP2 summary, reserve/use, CSV and history then work on the upgraded data (`08`).
  - T03. Reservation checks the balance inside BEGIN IMMEDIATE (`writeTransaction` uses `.immediate()`). On separate OS processes, exactly one of 80/80 at 100 wins in 30/30 rounds and in 20/20 with a lock blocker; two of 4×80 at 200 win in 20/20. Double consume, double reverse and cancel-versus-use keep the counters and ledger consistent in 20/20 rounds each. The same harness double-books 10/10 when the transaction is removed, even without an artificial window (`06`). E-5: 409 `insufficient_balance`, nothing created (P1). E-3: one second before local midnight in America/Los_Angeles is 409 `before_leave_date`; at local midnight the use posts −480 (P6). Partial use, exact-remainder use, same-key retry (also with a stale version) as `duplicate`, a different payload as `source_key_conflict`, use after cancel refused (P2). Reversal is bounded by consumed − reversed, needs a reason, and use/reverse cycles cannot create minutes (P3.6). Minutes convert 1:1 (480). LG-10: day label and leave-minute edits change no balance, ledger row or reservation (P9).
  - Harness. The authors' `worker_threads` harness gives each racer its own connection on one WAL file and releases them with a barrier; call windows overlapped in every round. Its self-check forces interleaving with an in-operation barrier, so the sensitivity proof is the authors' mutation log (`WP2-T03/04-mutation-reserve-without-transaction.log`: 3 races fail). ID swaps by a second employee and by an admin on consume, cancel and reverse give 404 `not_found`, byte-identical to an unknown ID, with no row, ledger or audit change (P7.1-P7.3). An admin sees only its own summary, ledger, leave list, CSV and history (P7.5). No credit, debit or correction route exists: the route inventory test passes and no router imports a posting function (grep). `expected_version` is required (422), stale gives 409, and the wrong type gives 422 (P7.7). Origin missing, `null`, foreign or another port gives 403; `text/plain` gives 415 (P7.8, authors' tests). Evidence CSV: `text/csv`, `attachment; filename="ot-evidence_<from>_<to>.csv"` (fixed alphabet), `no-store` and `nosniff` (P8.1). Hostile approver, identity, evidence, note and reversal-reason cells are apostrophe-prefixed and intact, no parsed cell starts with `= + @`, tab, CR or LF, and every row keeps its section width (P8.2-P8.5). No session gives 401; a reversed range or CRLF in the query gives 422 (P8.7). The content holds intervals, breaks, policies, daily raw/eligible/credited, ledger and leave permission, and on upgraded WP1 data it shows credited 90/120 and the WP1 leave minutes (PD9). History holds own events only; an admin-authored event shows `actor_is_self: false` and `actor_user_id: null`, and no other user's ID appears (P7.10-P7.11), apart from ADV-A-04.
- Authors' design notes, judged:
  1. 409 `source_key_conflict` on a reused key with a different payload: accepted (the fixtures README allows a typed duplicate error). It must also apply to corrections (ADV-A-01).
  2. A pending debit is returned, not persisted: accepted for WP2, which has no finalization. WP3 must store the pending proposal in the revision (R-05 "leaves it pending").
  3. No workflow clears the reconciliation flag: accepted. The balance flag is derived and clears when the balance recovers; the per-entry flag is an immutable posting fact. T11 and WP3 review must show it.
  4. Zero-minute credits are rejected: accepted (the schema forbids zero deltas). WP3 must post a credit, not a correction, when a day moves from 0 to a positive credit in a later revision, and must design its keys for that.
  5. No `leave_kind` on day entries yet: accepted. LG-10 is covered by label and leave-minute edits plus `approval_required`. T05 must add the `leave_kind = ot` case and the data for the E-2 mismatch warning.
  6. Provisional periods only for days with sessions: accepted, because credits need sessions (E-6). Iterating all history on every summary call should be revisited when WP4 imports history.
